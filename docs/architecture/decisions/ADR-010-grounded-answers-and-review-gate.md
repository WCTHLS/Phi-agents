# ADR-010: Grounded answers, stored runs and the review gate

- **Status:** Proposed (S2-09 core and S2-10 server side, built 4 Nov 2026). Awaiting review by the platform owner. The language model is not chosen yet (open questions Q3 and Q4), so no model is used.
- **Plain-language terms:** A *quote* is a stretch of words copied from a retrieved passage. *Verification* checks that every quote appears, word for word, in the passage it names. A *workflow run* is one question with its answer, its citations and its review status. *Withheld* means the system says it found no evidence instead of writing an answer. *Fail closed* means that if something needed for safety breaks, the action is refused.
- **Decision:**
  - **Answers are made only of verified quotes** (`features/research/answer_writer.py`, `answer_workflow.py`). An *answer writer* drafts quotes; `verify` keeps a quote only if it is found, ignoring line breaks and nothing else, in a passage that was actually retrieved. The text the user sees is built from the verified quotes and the names of their documents (`render_quotes`), never from anything else a writer returns, so a future language model cannot slip unverified prose into an answer. A quote that fails is removed and reported in the evidence gaps; an answer with no verified quote is **withheld** with a fixed "no verified evidence" message.
  - **No model yet: a quoting writer.** `QuotingAnswerWriter` picks, in each retrieved passage, up to two sentences that share the question's distinctive words (filler words removed, plurals folded) and quotes them exactly; at most six quotes. A passage that shares no distinctive word is not cited. A model-backed writer can replace it behind the same `AnswerWriter` interface (the choice waits on Q3 and Q4).
  - **Two numbers, named honestly.** `verified` means "every quote is word for word in a retrieved passage"; it does not mean the passage answers the question or is scientifically right. `confidence_score` is the share of the question's distinctive words found in the quotes (a coverage figure), not a probability.
  - **Runs are stored** (`workflow_runs`, migration 0005): the question and answer text, the citations, every passage returned with its ranks, the model name, and the status (`PENDING_EXPERT_REVIEW`, `APPROVED`, `REJECTED`, `EVIDENCE_REQUESTED`) with who decided and when. The server issues the run id (`RUN-` plus 12 hex characters). Question and answer text are stored here, behind the project membership checks; the audit trail keeps only a fingerprint of the question (ADR-005).
  - **The question endpoint uses the real search when `project_id` is given** (`POST /api/v1/research/query`). Membership is checked first (403 before anything is embedded); only that project is searched; the run and its audit event (`RESEARCH_QUERY_EXECUTED`, resource type `workflow_run`) are saved in one transaction. Without `project_id` the built-in sample passages are still used and the response says `data_source: built_in_sample`; that mode is to be removed (its callers are older tests and the smoke script). `publisher_filter` is refused (422) with a project, because it is not implemented there.
  - **The review endpoint checks the stored run** (`POST /api/v1/research/reviews`). Only `reviewer` and `qa` members of the project may decide (D15). The run must exist in the project in the request; a missing run and another project's run both give the same 404. The cited sources come from the stored answer, not from the browser, and the reviewer from the login token. The status change and the audit event (`ANSWER_REVIEW_APPROVED`, `ANSWER_REVIEW_REJECTED`, `ANSWER_EVIDENCE_REQUESTED`) are saved in one transaction. A run may be decided again; the latest decision is its status and the events are the full history.
  - **An audit event can join the caller's transaction.** `record_event(..., session=session)` adds the event to the caller's open database transaction and does not commit, so a change and the event that records it are saved together or not at all. Without `session` it behaves as before (its own transaction, for read-only actions). The in-memory test trail ignores `session`.
- **Why:** ADR-005 requires the sign-off record to be written by the server in the same transaction as the approval, and the review screen needs something real to approve. Verifying quotes mechanically is the only grounding check that works the same for a plain quoting writer and for a language model, and it is cheap to audit. Doing this without a model keeps the demo path unblocked by Q3 and Q4 while the design stays model-ready.
- **Trade-offs and limits:**
  - **A quote-only answer is not a synthesis.** It shows the evidence; it does not combine passages, compare documents or answer in the scientist's words. Whether quotes alone are enough for the demo is a product call.
  - **Verified does not mean correct.** The quoted sentence may be about a different substance, a different dosage form or a footnote. Wrong-passage answers are possible; the review gate and the "not yet reviewed by a domain expert" label (D9, D11) exist for this. No domain expert has reviewed any answer.
  - **No relevance floor beyond a shared word.** Any passage sharing a distinctive word with the question can be quoted. A question phrased entirely in words the documents do not use is withheld even if the meaning matches. Not yet measured on the golden questions.
  - **Coverage is a heuristic.** Plural folding is crude ("analysis" and "analysi" match each other and not much else), the stop-word list is short, and a number counts as a word.
  - **Nothing stops the asker from reviewing** unless they lack the `reviewer` and `qa` roles; the server does record who asked (`asked_by`) and who decided (`decided_by`) but does not compare them.
  - **The rationale and the answer are kept for good.** The rationale lives in an audit event that can never be edited or deleted; the question and answer text live in `workflow_runs`, which has no retention rule yet (open question 9 about retention).
  - **Runs are not listed or fetched by an endpoint yet.** The review screen's history is built from decisions made in the session; a `GET` for runs and their decisions is not built.
  - **Some audit writes still use their own transaction:** a refused request (403), a decision on a run that does not exist (404) and a failed search, because nothing else is changed in those cases.
  - **Concurrent decisions on one run** are both recorded; whichever commits last sets the status.
- **Revisit when:** the language model is chosen (write its `AnswerWriter`; decide whether prose between quotes is allowed and how it is verified); a domain expert reviews real answers; the sample mode is removed; retention rules are set; the review screen needs run history.
