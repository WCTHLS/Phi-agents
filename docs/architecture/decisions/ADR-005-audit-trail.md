# ADR-005: Audit trail written by the server, stored in the database

- **Status:** Proposed (S1-11). Changes how the audit viewer gets its data and removes one endpoint the frontend used, so it needs review by the frontend and platform owner.
- **Plain-language terms:** An *audit trail* is the permanent record that lets an auditor reconstruct who did what, to which object, when, and with what result. It is kept apart from ordinary logs, which developers read to fix bugs and may delete. *Fail closed* means that if something needed for safety is broken, the action is refused instead of going ahead without it.
- **Decision:**
  - **The server writes the events, not the browser.** When a real action happens (listing or opening a project, listing the source register, running a research query, reading the audit log), the API records it. The person is taken from the verified login token. The old endpoint `POST /api/v1/audit/events` is removed, because any logged-in user could use it to write any event for any project (for example a forged sign-off).
  - **Refused requests are recorded.** Every 403 for a logged-in caller is written as `ACCESS_DENIED` with outcome `DENIED`, including the project they tried to reach. 401s are not recorded, because nobody was identified.
  - **Who is recorded:** the stable subject ID from the token is stored as the actor, and the email in its own column (an email can change; the subject ID does not). All roles are stored, in a fixed order. The API shows the email in `actor_id` (what the viewer displays) and the stable ID in `actor_subject`.
  - **What is stored for a research question:** a fingerprint (SHA-256 and length), the sources retrieved, and counts, but not the question text, which may contain confidential product details (PRD FR-15). The trail can never be edited or deleted, so text put into it stays there.
  - **Two storage backends behind one interface.** `DatabaseAuditLogService` writes to the append-only `audit_events` table (triggers refuse update, delete and truncate; outcome is limited to SUCCESS, DENIED or FAILURE). `InMemoryAuditLogService` is for tests and database-less local runs; the app refuses it unless `ENVIRONMENT` is `local` or `test`. Choose with `AUDIT_BACKEND` (default `database`).
  - **Fail closed.** If the trail cannot be written, the API answers 503 and returns no data. A refused request is still refused if the write fails. The database wait is limited to 5 seconds. `/ready` reports 503 when the database does not answer.
  - **Reconstruction.** The admin list endpoint gains `resource_type`, `resource_id`, `since` and `until` filters; an auditor can ask for everything that happened to one object, in order. Reading the audit log is itself recorded (after the read, so a page never contains its own event).
  - The seed script records one real `DATABASE_SEEDED` event. The invented sample history is gone.
- **Why:** The sprint plan asks for an append-only record of who, what, when, object, version and outcome, written by the service layer, and PRD FR-30 and NFR-07 ask for an authoritative audit history separate from telemetry. A trail the client can write into is not authoritative. The ALCOA+ principle "attributable" needs the actor to come from the verified token, not from the request.
- **Trade-offs and limits:**
  - **No sign-off record exists yet.** The UI's sign-off screen used to post its own event; that call now gets 405 (the UI ignores the failure and keeps its local list). A real sign-off record has to be written by the server-side review gate (S2-10), in the same database transaction as the approval itself.
  - **Logins are not recorded by the API.** They happen in the identity provider (Keycloak or Entra ID), which keeps its own login events. The API records what people then do.
  - **A fingerprint is not encryption.** Someone who can guess the exact question could confirm it.
  - **Triggers stop the application, not a database owner,** who can still drop them. A restricted application role and per-row hash chaining (tamper evidence) are deployment hardening, not done here. The previous README claimed "tamper-evident"; it is append-only, not tamper-evident.
  - **Cost:** each protected request adds one database write, and each audit-log page view adds an event. Acceptable at this scale.
  - **Personal data:** the actor's email is stored in a table that is never deleted. Retention is an open client question (PRD open question 9).
  - **Audit writes use their own transaction.** That is correct for read-only actions. For state-changing actions (Sprint 2) the event must be written in the same transaction as the change.
- **Revisit when:** the review gate (S2-10) records approvals; the client sets retention rules; a restricted database role or hash chaining is added; login events from the identity provider need to join this trail.
