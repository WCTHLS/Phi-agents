# ADR-008: Chunking and embeddings

- **Status:** Proposed (S2-06, built 3 Nov 2026). Awaiting review by the platform owner.
- **Plain-language terms:** A *chunk* (or passage) is a short piece of a document, stored on its own so that a question can be matched to the passage that answers it. A *token* is the unit the embedding model reads: a word or a piece of a word. An *embedding* is a list of numbers (here 384) that stands for a passage's meaning: passages with similar meaning get similar numbers, and the database finds the closest ones. *Indexing* a document version means chunking its text and embedding every chunk.
- **Decision:**
  - **One pipeline, in four small parts.**
    - `features/documents/chunking.py` cuts page text into chunks. It is plain code with no model or database, and the same input always gives the same chunks.
    - `infrastructure/embeddings` holds the `Embedder` interface (`model_name`, `dimension`, `max_input_tokens`, `count_tokens`, `embed`) and the adapter for the local model (`local_model.py`, sentence-transformers, imported only when the model is created).
    - `features/documents/indexing.py` reads a version's stored page text, chunks it, embeds it and writes the rows.
    - `scripts/index_chunks.py` runs that for every ingested version. A future upload step can call the same service.
  - **How the text is cut** (the numbers are settings, see below):
    1. Page furniture is removed: page numbers, and short lines (not ending like a sentence) that repeat at the top or bottom of at least 40% of the pages, such as "Contains Nonbinding Recommendations". Nothing else is rewritten, so the words of a chunk are the words of the document.
    2. Wrapped lines are joined into paragraphs and paragraphs into sentences, across page breaks. Sentence splitting knows common abbreviations (`e.g.`, `Fig.`, `et al.`), initials and decimals.
    3. A heading starts a new section, and a chunk never crosses a heading. Contents-page lines (dot leaders) are dropped. A heading with no text under it makes no chunk.
    4. Sentences are packed into chunks of at most **500 tokens**; each chunk starts with whole sentences repeated from the end of the one before, up to **100 tokens** (ADR-003). A single sentence longer than the limit is cut into pieces of whole words.
  - **What a chunk records:** the pages it spans (`page_start`, `page_end`, from the pages its sentences start and end on), the nearest heading above it (`section`), its verbatim text, and its token count as the model's own tokenizer counts it. `char_start` and `char_end` stay empty: the page range plus the verbatim text is the citation.
  - **Embeddings:** `BAAI/bge-small-en-v1.5`, 384 numbers, scaled to unit length (decision D2, ADR-003). Every stored vector records the model's name. The service refuses a chunk size the model cannot read in full (the model silently cuts off anything beyond its limit, 512 tokens including two start and end markers, which would hide the end of a passage), and the adapter refuses a model whose vectors are not 384 long.
  - **Indexing rules.**
    - Only text of an eligible source is indexed (ADR-002).
    - A version with no selectable text (a scan; OCR is not available) is **skipped and reported**, never silently treated as indexed.
    - All chunks of a version are written together or not at all. The model runs before anything old is deleted, so a model failure leaves what was there. The caller commits, after the audit event, as in ingestion.
    - Indexing again with the same model changes nothing. Chunks made by a *different* model are replaced, never mixed, because vectors from two models cannot be compared. `--force` rebuilds.
    - The script writes an audit event `DOCUMENT_INDEXED` (actor `system:index-script`) for every version it changes, with the model, chunk count and chunking settings. It writes none when nothing changed.
  - **Settings** (`core/config.py`, environment): `EMBEDDING_MODEL`, `EMBEDDING_BATCH_SIZE`, `CHUNK_SIZE` (500 tokens), `CHUNK_OVERLAP` (100 tokens). `models_config.py` now defaults to the same model as ADR-003; before this it still named MiniLM.
  - **Install:** the library is in a new optional extra, `pip install -e ".[embeddings]"`. The API image and the dev tools container do not include it, so indexing runs on the developer's own machine for now.
- **Measured on 3 Nov 2026** (developer laptop: Windows, 16 GB RAM, no GPU; the 13 corpus PDFs; real model):
  - 13 versions became **673 chunks**. By the model's own tokenizer: smallest 7, median 367, largest 500 tokens. For all 673 the stored count equals an independent recount, none exceeds the limit, and all vectors have length 1.0000 and 384 numbers. 665 chunks have a section; the 8 without sit before the first heading of their document (title pages and the like).
  - Time: about **0.33 s per chunk** (32 real chunks in 10.6 s; the whole corpus took about 4 minutes). Loading the model took 29 s from the local cache; the first run, including the 128 MB download, took 210 s on this network. Installing the library took about 12 minutes on this network.
  - Memory: 574 MB after loading the model, **peak 909 MB** while embedding. ADR-003's table gives about 22 ms per chunk without saying how long the chunk was; the chunks measured here (median 367 tokens) took about 15 times as long.
  - **Nothing was lost to the cleaning rules**, checked by comparing every 3-word and 6-word run of the raw page text with the chunks: what is missing is running headers, contents lines, and runs that straddle a section heading (by design no chunk holds the end of one section and the start of the next). Two bugs found this way were fixed and have tests: a contents heading dropped the title block after it, and an identical last line on many pages was deleted as if it were a footer.
- **A first look at search quality** (a sanity check, not the S2-07 evaluation). The draft golden questions were embedded and searched with the database's nearest-neighbour query by `evals/retrieval_check.py` (the saved result is `evals/results/baseline-dense.json`, so later changes can be compared with it). A "hit" means a returned passage comes from the expected document and spans a page where the question's evidence patterns all appear.
  - Of 33 draft questions, **28 can be scored**. 3 need documents that are not ingested yet (the Indian rules) and 2 are gap questions whose right answer is "not covered". (Two questions, GQ-03 and GQ-06, could not be scored at first because their own evidence patterns matched no page; they were corrected on 3 Nov and 16 new ones added, see `data/sources/CORPUS.md`.) Meaning-only search finds the right passage in the top 5 for **24 of 28** and at rank 1 for 19 of 28; the right document in the top 5 for 27 of 28. Adding the model's recommended "query instruction" prefix changed nothing on the original 9 questions, so there is no basis yet to choose.
  - The 4 misses at the top 5, as far as they were examined: **GQ-01** returned the lead monograph ("Summary of PDE for Lead ... 5.0"), which does answer the question, but on a different page from the table the check accepts. **GQ-07** (named ICH M13A) found FDA's 2022 bioavailability guidance first. **GQ-09** needs two documents and only one came back. **GQ-32** (how quality risk management helps set specifications) was not examined.
  - Read this as: dense search alone is a workable start, and its weak spots are the ones predicted in the Sprint 2 checkpoint sheet (similar documents, questions that name a document, several documents at once, numeric tables). It says nothing about whether answers are scientifically right; no domain expert has reviewed any of it (decision D11).
- **Limits, not hidden:**
  - **Tables are text, not tables.** The PDF reader returns a table as a run of words, so a table is chunked like prose and a numeric question can miss it. Two mitigations were added on 6 Nov (decision log D26): each search keeps 50 candidates before merging, and the model may quote an excerpt (headings and rows) from a table passage. Tables are still not structured data and their numbers are not verified values.
  - **The section label is a best guess.** Headings are recognised by shape (numbering, capitals, PART/APPENDIX), checked against the corpus but not perfect. Example found: in ICH Q3D the per-element monograph titles ("LEAD", "GOLD") are not recognised, so their text carries the label `REFERENCES` from the section before. Four-letter capitals were tried and rejected: they added 2 correct headings and 7 wrong ones (chemical formulas, abbreviations). The page range and the verbatim text are the reliable parts of a citation; show the section as approximate.
  - **Damaged words stay damaged.** The PDF reader sometimes splits letters ("regulator y", "N -Methylpyrrolidone"). The text is kept as extracted; exact-word matching, once added, will miss those words.
  - **Page furniture is heuristic.** A repeated header that ends like a sentence is kept (safe: nothing is deleted); a one-off header is not recognised.
  - **A passage's page is a range.** A passage that crosses a page break records `page_start` and `page_end`; it is not one page. A citation's own page is found later by searching the quote in the stored page text (ADR-010). Symbol-font bullets in some PDFs (for example the lists in ICH Q3D) come out as a private-use character and display as an empty box; the words are intact.
  - **No unit tests prove retrieval quality.** The tests use a stand-in embedding model that counts words, to check the plumbing. The real model is checked by running the script.
- **Not done here, for S2-07 and later:**
  - ~~`search_nearest` does not limit results to the current model or the newest version.~~ Done in S2-07 step 1: `search_nearest` now requires the embedding model's name and by default searches only the newest version of each document (`latest_only=False` includes older ones).
  - The question must be embedded by the same model when searching; the API image does not include the library yet (it adds roughly a gigabyte, so decide how the API gets the model, or whether it calls a separate service).
  - The upload endpoint does not index; documents are indexed by running the script.
  - To try, with the golden questions as the measure: put the document title and section in front of each chunk before embedding (this may help questions that name a document); keyword matching alongside vector search; searching each named document separately.
  - Other heading and table handling (Tika layout, a table-aware reader) and OCR for scans.
- **Revisit when:** the model or chunk size changes (run `--force`); the retrieval check above gets worse after a change; OCR or a table-aware reader arrives; the corpus grows past what one script run can embed in a sitting; or the platform owner asks for indexing to run inside the API or a worker (`workers/README.md` plans an `embeddings_indexing` queue).
